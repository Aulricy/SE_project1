# 预约与交易实现说明

本模块承接实验二的 Reservation、ReservationService、OperationRequestRecord、OperationLog 设计，
对应 REQ-007、REQ-008、REQ-009、REQ-010、REQ-012、REQ-013、REQ-016、REQ-018、REQ-019。

## 状态与权限

| 操作 | 执行人 | 预约前置状态 | 商品前置状态 | 成功结果 |
|---|---|---|---|---|
| 预约 | 非所属卖家的普通用户 | 无有效预约 | 已发布 | 待卖家确认 / 已预约 |
| 确认 | 所属卖家 | 待卖家确认 | 已预约 | 已确认 / 已确认 |
| 取消或拒绝 | 预约买家或所属卖家 | 待卖家确认或已确认 | 对应的已预约或已确认 | 已取消 / 已发布 |
| 确认完成 | 预约买家 | 已确认 | 已确认 | 已完成 / 已完成 |

取消或拒绝必须填写原因，保存取消人、原因、时间；卖家拒绝待确认预约也使用取消流程。
没有自动超时、自动恢复、候补、线上付款或代替买家完成交易的入口。
旧页面的版本不匹配时失败并提示刷新，不允许待确认时的旧取消请求在确认后直接生效。
刷新后获得新版本和新请求标识，双方仍可主动取消已确认预约。
已完成交易不能取消、重发或重复计入完成记录。

浏览器传入的 buyer_id、seller_id、actor、role、reserved_price 等额外字段不能决定身份或预约价格。
身份由数据库登录会话确定，权限由服务端检查。管理员不能代替买卖双方操作预约。
记录、描述和图片仅对相关买卖双方可见；无关普通账号访问详情返回 404。

## 四类记录一起提交

每次成功操作在同一个 SQLAlchemy Session、同一个数据库事务中保存：

1. 商品状态和商品版本；
2. 预约状态、预约版本及适用处理时间；
3. 持久的成功请求记录；
4. 关联商品和预约的关键操作日志，含前后状态及适用原因。

任一写入或提交前步骤失败，所有本次变化一起回滚。成功标识不会在业务失败时单独留下。
日志和请求记录不能通过业务接口修改或删除。

针对当前 SQLite，事务第一条 SQL 对目标行执行不改变版本的 UPDATE，先取得数据库写入锁，
再读成功请求记录与当前业务状态，避免先读取旧快照再升级写锁。
商品模块同样检查版本和有效预约；两模块竞争同一商品时，只允许符合当前状态的一方成功。
应用没有使用进程内锁代替数据库并发控制。

数据库还提供两层约束：

- reservations 的条件唯一索引：同一 product_id 的 PENDING_CONFIRMATION、CONFIRMED 合计最多一条。
- operation_requests 的唯一约束：operator_id + request_key 唯一，跨商品和操作类型生效。

取消和完成记录不占用“有效预约”名额；正常取消后可以主动建立新预约，新记录不覆盖旧记录。

## 重复请求规则

每个表单生成一个新的随机 request_key。长度 16–128，仅接受字母、数字、下划线和连字符。
请求指纹使用操作类型、目标编号、原页面版本，以及取消请求的原始原因字符串。
只对已接受的参数计算指纹，不接受客户端设置身份、状态、价格或时间。

- 同一操作人、同一标识、相同内容：返回原预约的当前状态，不新建、不推进、不重复写成功日志。
- 同一操作人、同一标识、不同内容：409 冲突，要求明确发起新操作。
- 失败请求不持久占用标识；修正失败输入可以重新提交，仍需通过当前状态和版本检查。
- 原预约已取消或完成后，旧成功请求重发仍返回原记录，不恢复预约、不释放他人的新预约。
- 成功记录保存在数据库中，应用重启后仍能识别原请求。

页面在确认对话框后提交；成功使用 303 跳转到预约详情。
取消校验失败或旧版本冲突时保留原请求标识、原版本和已填原因，不静默改成当前版本重试。
已登录用户从商品详情预约只需“立即预约 + 确认操作”两次点击。

## 历史、时间与图片

预约价格按整数“分”捕获，属性 reserved_price 返回 Decimal；商品后续改价不改变旧预约金额。
完成时间只在首次成功完成时设置；重复完成返回原结果，不重写时间。
数据库使用 UTC，页面按北京时间展示。

在原 UML 字段基础上，补充保存预约时的名称和描述快照，用于历史显示。
因此，取消后卖家改草稿或重新发布，不会改写旧记录的名称、联系方式和交付说明。
图片没有另外复制历史版本：有效/已完成预约可读对应商品图片，当前公开图片也可读；
旧买家不能通过已取消预约查看卖家后来编辑的私有草稿图片。所属卖家仍可查看自己的图片。

## 页面入口

- /products/<id>：已发布商品的“立即预约”，不允许预约本人商品。
- POST /products/<id>/reserve：提交商品版本、请求标识和 CSRF。
- /reservations：我的预约，买入/卖出记录，按状态、商品编号查询，每页 12 条。
- /reservations/<id>：相关双方的预约详情、描述、价格、时间及处理原因。
- POST /reservations/<id>/actions/confirm：卖家确认。
- POST /reservations/<id>/actions/cancel：双方取消或卖家拒绝，原因必填。
- POST /reservations/<id>/actions/complete：买家确认完成。
- /reservations/<id>/image：与预约详情一致的参与者检查及额外图片可见性检查。

所有写入口均要求 POST 与真实 CSRF，页面按钮是否可见不能替代后端授权。
商品进入已预约、已确认后退出公开列表，但买卖双方仍能通过“我的预约”查看原描述和处理结果。
管理员屏蔽/恢复、完成交易统计及只读日志界面已接入，详见 admin.md。

## 旧数据库升级

重新执行 init-db 会创建预约与请求表，并兼容升级上一阶段的 operation_logs：
增加预约关联及预约前后状态，扩展日志操作类型约束，保留旧日志的编号、时间、原因和全部原字段。
升级过程在一个事务中复制并核对行数、替换旧表及重建原索引；中途异常会恢复原表。
只处理本项目已知的旧表结构；遇到额外自定义索引、触发器或不匹配的结构，不猜测修改。
不会清空用户、商品、会话或历史记录。本机升级前另存数据库备份到 instance/backups。

## 可复现验证

以下命令在 code 目录执行：

```powershell
.\.venv\Scripts\python.exe -m flask --app app init-db
.\.venv\Scripts\python.exe -m pytest
.\.venv\Scripts\python.exe -m pylint app tests tools
.\.venv\Scripts\python.exe -m tools.verify_reservation_races
```

集成测试使用独立 SQLite 文件和上传目录，覆盖正常完成、双方取消、价格与描述历史、
越权、私有图片、数据库唯一约束、四类记录写入失败回滚、提交前中断及升级中断回滚。

并发测试包括 10 买家抢同一商品；同键预约、确认、取消、完成并发重发；
同一操作人的标识跨商品竞争；确认/旧取消、完成/取消、预约/下架竞争；
旧预约和旧取消同时重放后，新有效预约仍保持不变。

HTTP 工具另外通过真实登录、真实 CSRF 和独立 Cookie 客户端运行五类竞争场景，
保留全部 34 次竞争请求的状态、耗时和提交后数据库状态。预期失败方的 409 不会被排除。
工具结果写入 instance/reservation-race-check.json，隔离数据库结束后清理。
测试生成数据不代表真实用户、申请、交易或实际收款。
